# 주간 식단 API 캐시

## 사용하는 방법

- 참여 화면의 **주간 식단** 또는 `/menu`로 접속한다.
- 현재 지정한 원본은 정글 식당 채널의 **11월 2주차 식단표**, 게시글 번호 `114707701`이다. 최신 주를 자동 선택하지 않는다.
- 관리자 기능은 `/admin`에서 기존 관리자 키로 인증한 뒤 주간 식단 페이지로 이동하면 나타난다.
- **식단 캐시 비우기 → 식단 다시 조회**: `MISS` 표시. 다른 기기나 같은 화면에서 다시 조회하면 `HIT` 표시.
- **사용 전후 5회씩 비교**: 실제 원본 5회와 예열된 공통 캐시 5회의 평균·중앙값·최소·최대 시간을 비교한다. 비교 시작 시 첫 원본 결과로 공통 캐시를 새로 채운다.

화면 위쪽에는 이번 조회 시간과 마지막 조회 기준 캐시 잔여 시간을 큰 숫자로 표시한다.
PC에서는 식단 제목과 두 지표를 한 줄에 모으고 여백을 줄여 첫 화면부터 식단 이미지 일부를 볼 수 있다.
휴대폰에서는 제목 아래에 지표 두 개를 나란히 표시한다. 별도 발표 화면 메뉴는 사용하지 않는다.
남은 시간은 브라우저에서 계산하며 다른 기기의 캐시 삭제 여부를 실시간으로 조회하지 않는다.
실제 유효 여부는 다음 조회 시 C 저장소가 판단한다. 관리자 조작 버튼과 비교 결과도 식단 이미지 위에 표시한다.
일반 참여자의 화면에는 관리자 버튼과 긴 구현 설명을 표시하지 않는다.
상태 문구는 제목과 다시 조회 버튼 사이의 고정 높이 영역에 표시한다.
모바일에서는 같은 영역을 제목 바로 아래에 확보하며 알림이 나타나도 아래 카드·이미지를 밀지 않는다.
화면 조작은 캐시 비우기와 성능 비교 두 가지로 정리했다. 원본 직접 조회 버튼은 제거했다.

## 저장 구조와 동작

`Flask /api/menu → C Mini Redis GET → 없으면 카카오 원본 → 제목/이미지 주소 정리 → C Mini Redis SET TTL 3600000ms → JSON 응답`

키는 `jungle:seats:v1:cache:menu:114707701`이다. 값에는 식단 제목, 이미지 주소, 원본 게시글 링크와 원본 조회 시각이 들어간다. 모든 브라우저가 같은 키를 사용한다. 처음 저장한 뒤 1시간이며 HIT로 연장하지 않는다. 접근 시 만료 확인은 C 저장소가 담당한다. 캐시 값도 기존 변경 로그에 기록되므로 저장소 재시작 후 유효한 기한이 남으면 복구한다.

한 웹 프로세스 안에서 공통 락으로 초기 원본 요청을 하나로 모으고 삭제와도 직렬화한다. 여러 Flask 프로세스로 확장할 경우에는 분산 조정이 필요하다. 현재 서버는 교육용 단일 프로세스 구성이다.

API:

- `GET /api/menu`: `{menu, cache: HIT|MISS, elapsed_ms, fetched_at_ms, expires_at_ms, ttl_seconds}`
- `POST /api/admin/menu/origin`, 본문 `{}`: 캐시를 읽거나 갱신하지 않는 BYPASS 응답
- `POST /api/admin/menu/clear`, 본문 `{}`: 식단 키만 삭제. 좌석과 참여자 키에는 영향 없음
- `POST /api/admin/menu/benchmark`, 본문 `{}`: 5회씩 비교 결과와 응답 내용 동일 여부. 관리자·Origin·본문 검사는 기존 웹 규칙 사용

## 원본 연결과 한계

카카오 페이지가 사용하는 JSON 조회 주소를 읽는다. 공식적으로 지원되는 공개 개발자 API 계약은 아니므로 주소나 응답 형식이 바뀌면 연결 코드를 수정해야 한다. 주소는 코드에 고정하고 사용자가 임의 URL을 입력할 수 없게 했다. 리디렉션은 따라가지 않고, 원본 요청은 5초 타임아웃과 256KiB 상한을 둔다. 제목·게시글 번호·이미지 도메인을 검사하며 원본 실패를 정상 캐시로 저장하지 않는다. 오류 시 502, 저장소 연결 실패 시 503을 반환한다.

이미지 URL은 `https://k.kakaocdn.net`만 허용한다. 이미지 자체는 브라우저가 별도로 내려받는다. OCR로 이미지 속 메뉴를 추출하지 않는다. 식단 변경은 최대 1시간 늦게 반영될 수 있고 관리자가 캐시를 비워 바로 갱신할 수 있다. 원본 장애 동안에는 기존 캐시가 유효한 동안만 조회할 수 있다.

## 성능 비교 해석

2026-11-14 실제 연결의 첫 실행 결과(`docs/menu-benchmark.json`):

| 모드 | 횟수 | 평균 ms | 중앙값 ms | 최소–최대 ms |
| --- | ---: | ---: | ---: | ---: |
| 캐시 없음: 실제 카카오 요청 | 5 | 38.471 | 39.651 | 32.634–42.450 |
| 캐시 있음: Mini Redis 조회 | 5 | 0.418 | 0.418 | 0.354–0.502 |

모든 응답의 식단 내용은 같았다. 외부 요청은 5회다. 첫 원본 결과를 캐시에 저장한 예열 작업은 HIT 측정에 포함하지 않는다. 이후 네 번은 원본·HIT를 번갈아 측정한다. 인위적인 대기 시간을 넣지 않는다.

이것은 웹 서버 내부의 응답 생성 시간 비교다. 브라우저와 웹 서버 사이의 왕복, 이미지 다운로드, 렌더링 시간은 제외한다. 외부 HTTPS 통신과 JSON 처리 비용을 캐시가 줄이는 효과이며 C 해시 테이블 자체의 벤치마크나 Redis 제품과의 비교가 아니다. 5회 소규모 측정은 발표용이며 부하·처리량·일반적인 성능 보장을 뜻하지 않는다. 환경에 따라 결과가 달라지며 측정 중 식단이 변경되면 같은 내용의 비교가 아님을 화면에 알린다.

## 검증

`make menu-test`: 실제 별도 C 서버와 임시 로그를 사용한다. 서로 다른 클라이언트의 캐시 공유, HIT 기한 유지, 만료·삭제 후 재조회, 동시 캐시 채우기, 오류 미저장, 권한, 입력 검증, 비교의 원본 호출 횟수와 내용 동일성, 변경 감지, BYPASS 미갱신을 검사한다. 실제 외부 요청은 자동 테스트에 넣지 않는다.

실제 카카오 연결로 MISS/HIT, 관리자 삭제, 비교 버튼, 이미지 로딩을 확인했다. 390px 휴대폰 너비에서 가로 넘침 없이 표시되는 것을 확인했다. 결과 화면은 `docs/screenshots/menu-benchmark.png`, 휴대폰 화면은 `docs/screenshots/menu-mobile.png`에 저장했다.
