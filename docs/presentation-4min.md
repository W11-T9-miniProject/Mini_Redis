# Redis 발표 후보 — 설명 2분 + 실제 데모 2분

**주제:** 같은 데이터를 함께 쓰는 사람들 사이에서, 빠르게 읽고 안전하게 선점하기.

**청중에게 남길 한 문장:** 직접 만든 인메모리 키·값 저장소를 자리 선점과 식단 응답 캐시에 연결했다.

## 앞 2분: README를 보며 설명

README 첫 문단과 인메모리·캐시 표 → 직접 구현한 내용 표 → 캐시 그림 → 자리 선점 그림 → 검증 결과 순서로 설명한다. 무엇을 직접 구현했는지 먼저 말하고 그림은 동작을 짚는 데 사용한다. 아래 시간·조작·대본은 발표자용 자료이며 프로젝트 README에 진행 멘트로 넣지 않는다.

아래는 읽을 대본 초안이다. 구조와 화면을 가리키는 시간을 포함해 약2분을 목표로 리허설한다.

> 이번 구현을 두 단어로 설명하면 인메모리와 캐시입니다. 인메모리는 키와 값을 RAM에 보관한다는 뜻이고, 캐시는 이미 가져온 응답을 저장해 다음 요청에서 재사용한다는 뜻입니다. 저희는 C로 만든 인메모리 저장소를 실제 API 응답 캐시에 연결했습니다.
>
> 같은 식단을 여러 사람이 볼 때마다 원본 서버에 요청하면 같은 통신과 응답 처리 비용이 반복됩니다. 유효한 응답을 저장해 다시 사용하면 그 비용을 줄일 수 있습니다. 캐시는 이 재사용 방식이고, 인메모리는 저희가 그 값을 보관한 방식입니다.
>
> 직접 구현한 핵심은 해시 테이블입니다. 해시 함수로 키의 저장 위치를 구하고, 충돌은 체이닝으로 처리하며 데이터가 늘면 리해싱합니다. 여기에 저장·조회·삭제와 만료, 조건부 저장을 구현하고 외부에서 쓰도록 HTTP API를 연결했습니다.
>
> 식단 응답이 없으면 원본에서 가져와 저장하는 MISS, 유효한 값이 있으면 재사용하는 HIT로 처리합니다. 기한은 최초 저장부터 10분이며 조회로 늘어나지 않습니다. 관리자가 캐시를 비우면 다음 요청에서 원본을 다시 가져옵니다. 같은 내용의 원본 조회와 캐시 조회 시간을 비교했습니다.
>
> 같은 저장소를 자리 선점에도 사용했습니다. NX는 유효한 키가 없을 때만 저장하는 조건이고, 공통 락인 뮤텍스로 키 확인부터 저장까지 보호합니다. 임시 선점은 20초이며, 만료된 값은 접근할 때 제거합니다. 관리자 취소는 기한 전의 명시적 무효화입니다. RAM이 사라져도 복원할 수 있도록 AOF 방식으로 변경 로그를 남기고 디스크 반영 후 성공을 응답합니다.
>
> 저장·조회·삭제 단위 테스트와 HTTP·웹 기능 테스트를 수행했고, 동시 선점, 만료 경계와 실패 상황도 확인했습니다. 이제 자리 선점·만료와 캐시 재사용을 화면에서 보여드리겠습니다.

README에서 가리킬 구조는 이것이면 충분하다.

```text
자리 화면·식단 화면 → 웹 서버 → C Mini Redis → RAM의 해시 테이블
                                           ↕
                                      디스크의 변경 로그
```

## 뒤 2분: 이미 만든 화면 두 개로 시연

발표자가 미리 준비한 일반 브라우저 A와 시크릿/다른 브라우저 B를 사용한다. QR 전체 참여는4분 안에 대기·등록 시간을 예측하기 어려워 이번 기본 시연에서 사용하지 않는다.

| 전체 발표 시간 | 실제 조작 | 화면에서 짚을 것·설명 |
| --- | --- | --- |
| 2:00~2:25 | A가2팀-2 임시 선점, B의 같은 자리 상태 확인. 확정하지 않고20초 카운트다운을 보여줌 | “유효한 선점이 있는 동안 다른 사람이 같은 자리를 가져갈 수 없습니다. 시간 판정은 화면이 아니라 저장소가 합니다.” |
| 2:25~2:45 | 만료 후 B가 같은 자리를 선점하고 확정 | “기간이 끝난 값을 다시 사용할 수 있는 상태로 바꿉니다. 만료된 키는 접근할 때 정리합니다.” |
| 2:45~3:00 | 관리자 화면에서 B의 배정 취소 | “시간 경과와 별도로, 명시적인 무효화도 제공합니다.” |
| 3:00~3:45 | 관리자 인증된 /menu에서 캐시 비우기 → 식단 다시 조회(MISS) → 다시 조회(HIT). 여유가 있으면5회 성능 비교 버튼 | “처음에는 원본을 가져와 저장하고, 다음에는 같은 저장 응답을 재사용합니다. 표시된 시간과 출처가 달라집니다.” |
| 3:45~4:00 | 캐시 비교 또는 HIT 화면에서 마무리 | “공유 상태의 원자적 갱신과 반복 조회 재사용을 같은 저장소로 연결했습니다.” |

창 전환과20초 기다림이 있으므로 미리 리허설한다. 시간 부족 시5회 성능 비교 버튼을 생략한다. 서버 종료·복원은 기본2분 데모에 억지로 넣지 않고 README 검증 결과·Q&A로 설명한다.

## 발표 전 준비

Mini_Redis를 연 Ubuntu 컨테이너의 서로 다른 두 터미널에서:

```bash
# 첫 터미널: 저장소. 이미 실행 중이면 다시 실행하지 않는다.
make server
./build/mini-redis-server
```

```bash
# 두 번째 터미널: 웹
make web
```

- VS Code Ports에서8090 전달 후 PC의 http://127.0.0.1:8090/ 접속. 자리 화면 A·B와 관리자 /admin, 관리자 인증된 /menu 탭을 미리 연다. 브라우저 글씨를 키워 뒤에서도 읽히게 한다.
- A/B는 서로 다른 브라우저 세션과 다른 교육생 번호로 사전 등록한다. 예를 들어 데모 참가자 A/9001, B/9002처럼 허용 범위 내 사용하지 않는 시연용 번호를 쓸 수 있다. 번호는 본인 인증 수단이 아니다.
- 관리자 인증 키는 data/web-admin.key에서 확인한다. 화면 공유 중 키를 노출하지 않는다. 이미 인증한 세션을 사용한다.
- 두 시연 자리2팀-2·11팀-1을 비워 두고, 다른 자리를 시연 중 취소했다면 ‘기존 배정으로 되돌리기’로 복구한다. 로그 파일 전체 삭제·FLUSHALL로 초기화하지 않는다.
- 공통 배정 만료 시각은 발표 종료보다 뒤로 맞춘다. 이전에 설정한 과거 시각 때문에 확정이 실패하지 않는지 리허설한다. A/B가 이전 선점을 가지고 있으면 먼저 취소해 둔다.
- /menu를 열면 자동 조회가 일어나므로, 실제 MISS를 보여줄 직전에 ‘캐시 비우기’를 누른 뒤 ‘식단 다시 조회’를 누른다. 버튼 이름과 동작은 현재 화면 기준으로 확인했다.
- 식단은 지정된 예제 게시글을 조회하며 최신 주차 자동 검색 기능이 아니다. 원본 연결을 발표 전에 확인한다. PC 로컬 자리 시연은 외부 터널 없이 가능하고, 식단 원본 조회는 인터넷이 필요하다.

## 보여준 것과 검증한 것 구분

- 자리 화면에서 선점이 공유되는 관찰과, 실제 동시 NX 요청의 원자성 검증은 다르다. UI만으로 동시성의 모든 경우를 증명했다고 말하지 않는다. README에는100개 동시 NX 요청 중 하나만 성공한 테스트 근거를 짧게 둔다.
- 캐시하는 것은 식단 제목·이미지 주소 등의 API 응답이다. 이미지 파일 자체는 브라우저가 별도로 받는다. 조회 시간은 이미지 다운로드·화면 렌더링을 포함하지 않는다.
- 실측 캐시 비교는 외부 원본 요청과 캐시 응답의 비용 차이다. 상용 Redis보다 빠르다는 결과나 C 해시 조회만의 벤치마크가 아니다.
- 만료와 관리자 취소는 구분한다. 만료는 기한에 따른 유효성 종료, 취소·캐시 비우기는 사용자가 명시적으로 무효화하는 동작이다.

현재 자리·캐시 기능의 기존 코드와 문서를 기준으로 만든 시연안이다. 이번 준비에서는 실제 배정을 바꾸거나 원본 연결을 새로 확인하지 않았다. 발표 전에 화면·인증·초기 상태와 시간 배분을 한 번 더 실행해 확인해야 한다.

식단 원본에 오류가 나면 한 번만 확인하고 [사전 실측 화면](screenshots/menu-benchmark.png)으로 전환해 “이것은 사전 실행 결과”라고 설명한다. [자리 화면 예시](screenshots/seat-u-order.png)도 보조 자료로 사용할 수 있다. 캡처는 라이브 성공으로 소개하지 않는다. 구체적 실행·한계는 [자리 시연 안내](seat-demo.md)와 [식단 캐시 안내](menu-cache.md)를 참고한다.

Q&A 대비는 세 개만 먼저 준비한다.

- **dict로도 가능한가?** 한 프로세스 내부 캐시는 가능하다. 별도 저장소는 여러 클라이언트가 공통 상태를 사용하고 원자 연산·만료 등의 정책을 공유하는 데 의미가 있다.
- **왜 락이 필요한가?** NX의 ‘없음 확인’과 ‘저장’ 사이에 다른 요청이 끼어들지 않게 전체 연산을 보호해야 한다.
- **꺼지면 RAM은 사라지는데?** 변경 로그를 파일에 기록·동기화하고 시작 시 복원한다. 성공 응답 전 처리를 검증했지만 물리적 전원 장애나 모든 저장장치 고장을 보장하는 것은 아니다.
