# Mini Redis 설계 초안

상태: 사용자와 합의한 선택을 정리한 초안. 마지막 절의 결정은 추가 논의 후 반영한다.

## 목표와 범위

C로 범용 키-값 저장소를 직접 구현한다. 결과물뿐 아니라 해시 테이블,
메모리 소유권, 동시성, 만료, 영속성의 동작과 선택 이유를 설명할 수 있어야 한다.
각자 구현한 결과를 공유하며, 구현에 사용할 수 있는 기간은 약 2~3일이다.

웹 화면과 자리 선점 서버는 최소한의 사용 예제로 만든다.
핵심 학습 대상은 C 저장소이고, 웹 프레임워크 내부 원리는 이번 범위에서 제외한다.
기존 Redis와의 프로토콜 호환은 목표에 포함하지 않는다.
실습용 Docker Redis와 직접 구현할 Mini Redis는 별개다.

## 구성과 환경

```text
휴대폰 웹 화면 → 자리 선점 서버 → C Mini Redis HTTP API → 해시 테이블
```

- Windows의 VS Code와 Docker Dev Containers를 사용한다.
- Ubuntu 22.04에서 GCC, pthread mutex, fsync를 사용한다.
- 개발 이미지 빌드 및 도구 실행을 검증했고, 사용자가 VS Code 연결을 확인했다.
- HTTP 공통 처리는 라이브러리에 맡긴다. 저장소 로직은 직접 구현한다.
- Mini Redis는 자리나 사용자의 의미를 해석하지 않는다.
- 웹 서버가 자리 규칙과 사용자·관리자 권한을 확인한다.

## 해시 테이블

- 키와 값은 문자열이다. 빈 값과 없는 키를 구분한다.
- 해시 함수는 FNV-1a 64비트, 초기 버킷 수는 16이다.
  16은 최적화 측정값이 아니라 빈 배열 메모리와 초반 확장 횟수 사이의 시작 기준이다.
- 충돌은 버킷별 단일 연결 리스트로 해결한다.
- 다른 키가 같은 버킷에 들어와도 기존 항목을 덮어쓰지 않는다.
- 같은 키에 일반 저장하면 기존 값을 교체한다.
- 새 항목 추가로 항목 수 / 버킷 수가 1.0을 넘게 되면 버킷 수를 두 배로 늘린다.
- 확장 시 모든 노드의 버킷 위치를 다시 계산한다. 값 변경은 항목 수를 늘리지 않는다.
- 확장은 공통 락 안에서 한 번에 수행한다. 그동안 다른 저장소 요청은 기다린다.
- 체이닝 선택 이유는 삭제·만료 구현의 단순성과 제한된 일정이다.
  실행 속도나 메모리가 언제나 개방 주소법보다 유리하다는 주장은 하지 않는다.

## 메모리 소유권

- 저장소는 키와 값을 별도 메모리에 복사해서 소유한다.
- 삭제·만료·교체 시 더 이상 사용하지 않는 메모리를 해제한다.
- 조회는 공통 락 안에서 값을 복사한 뒤 락을 해제한다.
- 호출자는 반환된 복사본을 사용한 뒤 해제한다.
- 할당 실패는 오류로 반환한다. 기존 데이터를 먼저 잃어서는 안 된다.

## 연산과 동시성

| 연산 | 규칙 |
| --- | --- |
| 일반 저장 | 없으면 추가, 있으면 교체 |
| NX 저장 | 유효한 키가 없을 때만 저장 |
| 조회 | 유효한 값의 복사본 또는 키 없음 |
| 삭제 | 키 삭제 |
| 조건부 삭제 | 현재 값이 예상 값과 같을 때만 삭제 |
| 조건부 변경 | 현재 값이 예상 값과 같을 때만 값과 만료 시각 변경 |

테이블 전체를 보호하는 mutex는 하나다. 공유 테이블에 접근하는 모든 경로가
같은 락 규칙을 지킨다. NX 및 조건부 연산은 조회·만료 확인·비교·변경 전체를
하나의 임계 구역에서 처리한다. HTTP 해석과 응답 전송은 락 밖에서 수행한다.

서로 다른 버킷의 작업도 기다릴 수 있다. 락 대기는 예약 대기 명단이 아니며,
클릭 순서나 네트워크 도착 순서대로 성공한다는 공정성은 보장하지 않는다.

## 만료

- 각 항목에 절대 만료 시각을 보관하고, 만료 없음은 구분해 표현한다.
- 상대 유효기간은 서버의 현재 시각에 더해 절대 시각으로 변환한다.
- 현재 시각이 만료 시각 이상이면 유효하지 않다.
- 조회·NX·조건부 연산 등 해당 키에 접근할 때 만료를 확인한다.
- 만료된 항목은 제거하고 없는 키로 취급한다. 주기적인 전체 정리는 초기 범위에서 제외한다.
- 접근하지 않는 만료 데이터는 메모리에 남을 수 있지만 유효한 값으로 반환하지 않는다.
- 서버 시각을 기준으로 판단하며, 화면 카운트다운은 확정 권한의 기준이 아니다.
- 주간 배정은 각자 7일 뒤가 아니라 모두 같은 리셋 시각을 사용한다.

## 변경 로그와 복원

- 성공한 데이터 변경은 변경 로그로 남기고, 디스크 반영 성공 후 성공 응답한다.
- 초기 구현은 공통 락 안에서 로그 기록과 fsync까지 수행한다.
- 디스크 대기로 다른 저장소 작업이 기다리는 성능 비용을 수용한다.
- 재현할 로그는 결정된 변경 결과와 절대 만료 시각을 담아야 한다.
  재시작할 때 NX 조건을 다시 평가하거나 유효기간을 새로 시작하지 않는다.
- 필요한 메모리와 확장 공간은 로그 반영 전에 확보하여,
  로그가 확정됐는데 메모리에 반영하지 못하는 경우를 예방한다.
- 로그에는 기록의 경계와 완전성·손상을 검증할 정보를 둔다.
- 불완전한 마지막 기록은 적용하지 않는다. 다시 쓰기 전에 그 꼬리를 정리해야 한다.
- 중간 기록의 손상은 조용히 건너뛰지 않고 복원을 중단하여 알린다.
- 기록·동기화 오류가 발생하면 성공으로 응답하지 않는다.
  기록이 일부 반영됐을 가능성을 고려한 후속 쓰기 정책은 구현 전 논의한다.
- 복원 순서는 완전한 로그 재현 → 최종 상태의 만료 항목 제거 → 요청 접수다.
- 복원 작업은 로그를 다시 생성하지 않는다.
- 로그 파일은 개발 컨테이너 교체에도 남는 프로젝트 마운트 경로에 둔다.
- 정상 종료와 강제 종료를 구분하여 검증한다.
  fsync가 임의의 하드웨어 고장까지 절대적으로 보장한다고 설명하지 않는다.

## 자리 선점 시연

- 개인 자리 두 개만 선택 가능: 배치도 왼쪽 아래 초록 자리와 오른쪽 아래 초록 자리.
- 사용자가 설명한 배정상 각각 2팀과 11팀에 해당한다. 파란 코치 자리는 제외한다.
- 팀 구성은 1~10팀 각 3명, 11~12팀 각 2명이다.
- 선점 시마다 새 고유 선점 ID를 만든다. 사용자 ID와 선점 ID를 구분한다.
- 빈자리를 NX로 20초 임시 선점한다. 이미 선점 중이면 즉시 실패한다.
- 유효한 본인 선점만 확정할 수 있다. 확정 시 만료를 공통 리셋 시각으로 변경한다.
- 만료 후에는 새로 선점해야 한다. 실패한 요청은 자동 대기·배정되지 않는다.
- 사용자 취소는 선점 ID가 현재 값과 일치할 때만 삭제한다.
- 관리자 강제 취소는 웹 서버의 권한 확인 후 일반 삭제를 사용한다.
- 관리자 취소는 명시적 무효화, 시간 경과는 만료로 구분해 보여준다.
- 시연용 공통 리셋 시각의 예시는 한국 시간 11월 26일 14시다.
  실제 시연 일정에 맞게 설정값으로 지정한다.
- 서버 재시작 시 유효한 확정 배정은 복원하고 이미 만료된 선점은 되살리지 않는다.

성공 응답 유실 시 요청자는 성공·실패를 단정하지 않는다.
기존 선점 ID로 현재 상태를 조회하고, 조회도 실패하면 결과 확인 불가로 안내한다.
키가 없어도 과거에 저장되지 않았다는 증거는 아니다. 이미 만료됐을 수 있다.

## 검증 기준

### 단위·저장소 테스트

- 저장·조회·값 교체·없는 키·빈 값 구분.
- 의도적으로 충돌시킨 키의 독립 조회와 연결 리스트의 앞·중간·끝 삭제.
- 확장 후 기존 키 보존, 값 교체 시 항목 수 유지.
- 만료 직전·정각·이후, 만료된 키에 NX 저장.
- 오래된 선점 ID로 새 선점의 삭제·확정 불가.
- 응답 복사본의 수명과 메모리 해제 문제 검증.
- 같은 키에 충분히 긴 유효기간으로 NX 동시 요청:
  성공 정확히 하나, 나머지는 조건 불충족, 최종 값은 성공자의 ID.
- 로그 복원·강제 종료·불완전한 꼬리·중간 손상·만료 상태 복원.

### 기능 테스트와 성능 비교

- HTTP를 통해 저장소를 사용하는 기능 테스트.
- 자리 참여 시연과 별도로 API 응답을 저장·재사용하는 캐시 사례를 포함한다.
- 캐시 미사용·적중·미적중을 구분하고 같은 데이터와 요청 조건으로 비교한다.
- 응답 시간과 원본 조회 횟수를 확인한다. 속도 향상을 미리 보장하지 않는다.
- 원본 처리에 인위적 지연을 사용한다면 모의 실험임을 명시한다.
- 실제 자리 선점 판단은 캐시 화면이 아니라 현재 저장소의 원자적 연산을 따른다.

## 추가 설계에서 결정할 항목

이 절은 확정 사항이 아닌 후속 논의 목록이다.

1. 문자열·요청 크기 및 유효기간의 허용 범위.
2. HTTP 라이브러리와 JSON 처리 방식, 동시 요청 설정, API 주소·상태 코드·본문.
3. 로그의 실제 형식과 검증 방식, 파일 오류 후 동작, 파일 저장 경로.
4. 선점 값의 표현, 사용자 식별, 개인당 중복 선점 허용 여부와 필요한 보장.
5. 최소 웹 서버 기술과 휴대폰 접속 경로. 외부에 저장소 쓰기 API를 직접 노출하지 않는다.
6. 캐시할 원본 API와 무효화 규칙, 재현 가능한 성능 비교 조건.

이후 구현은 해시 테이블 → 만료·조건부 연산·락 → 로그·복원 → HTTP·사용 예제
순서로 작게 나누고, 각 단계에서 원리 설명·구현·테스트·선택 이유 정리를 연결한다.
